# Cadenza — 제품 정의

> 카덴차는 협주곡에서 오케스트라가 멈추고 연주자 혼자 남아 자기 이야기를 풀어놓는 구간이다.

## 한 문장

**클래식 곡에 얽힌 이야기를 읽고, 그 자리에서 곡을 듣는 곳.**

## 무엇이 아닌가

**음원을 트는 서비스가 아니다.** 그쪽으로 잡으면 Spotify와 카탈로그 싸움이 되고,
라이선스 비용이 개인 프로젝트의 범위를 벗어난다.

**스토리가 주인공이고 플레이어는 동반자다.** 이 포지션이 제품의 차별점이자
저작권 문제의 구조적 해법이다.

## 핵심 루프

1. 곡 목록에서 제목과 한 줄 소개를 본다
2. 곡 상세로 들어간다 — 플레이어가 위에, 이야기가 아래에
3. 재생을 걸어놓고 이야기를 읽는다

## 저작권 구조 — 설계의 전제

권리는 **2층**이다. 이 구분이 데이터 모델을 결정한다.

### 1층 — 작곡(악곡)

한국 저작권법상 저작재산권은 사후 70년. 단 2013-07-01 개정 이전에 이미 만료된 저작물은
보호가 부활하지 않으므로, 실무적으로 **1962년 말 이전에 사망한 작곡가의 작품은 퍼블릭 도메인**이다.

- 자유: 바흐, 베토벤, 쇼팽, 드뷔시(1918), 사티(1925), 라벨(1937), 라흐마니노프(1943), 프로코피예프(1953), 시벨리우스(1957)
- 보호 대상: 쇼스타코비치(1975), 브리튼(1976) — "클래식이니까 괜찮다"가 항상 참은 아니다

이 규칙은 `Composer.PUBLIC_DOMAIN_DEATH_YEAR_THRESHOLD` 에 코드로 박아 두었다.

### 2층 — 녹음(음원)

연주자의 실연권과 음반제작자의 저작인접권이 **별도로** 붙고, 한국은 발행 후 70년이다.

**베토벤은 자유지만 카라얀/베를린필의 1970년 녹음은 보호 대상이다.**
악곡이 PD라는 이유로 상업 음반을 가져다 호스팅하면 그대로 침해다.

### 그래서 운영 원칙

| 대상 | 방식 |
|---|---|
| PD 악곡 + PD/CC 음원 (Musopen, archive.org, Wikimedia) | 직접 호스팅 가능 |
| PD 악곡 + 상업 녹음 | **유튜브 공식 채널 임베드만** |
| 보호 중인 악곡 (사카모토 등) | **유튜브 공식 채널 임베드만** |

임베드 시 지킬 것:
- **공식 업로드만** 건다 (아티스트 공식 채널, 레이블, 오케스트라 공식). 팬 재업로드는 침해 방조 소지
- **오디오를 추출해 서버에 저장하지 않는다.** 재생은 반드시 그쪽 플레이어가 한다

### 텍스트도 저작물이다

음반 해설지(라이너 노트), 평론, 프로그램 노트는 보호 대상이다.
위키백과는 CC BY-SA라 출처 표기와 동일조건 이용허락이 따라붙는다.

**사실(작곡 연도, 초연 장소)에는 저작권이 없다. 사실만 가져와서 문장은 직접 쓴다.**

## 데이터 모델

```
Composer ─< Work ─< Recording
                     └ is_default 하나만 화면에 노출
```

### Composer
작곡가. `diedYear` 로 악곡의 PD 여부를 판정한다.

### Work
곡. **스토리가 붙는 단위이자 저작권 판정의 단위.**
본문은 Markdown 원문으로 저장하고 읽을 때 렌더링한다.

### Recording
한 곡의 특정 연주/음원. `sourceType` (`YOUTUBE` / `SELF_HOSTED`) 으로
**저작권 판단을 앱 로직이 아니라 필드 하나로 격리**한다.
덕분에 나중에 보호 중인 곡을 임베드로 추가해도 모델을 건드리지 않는다.

`license` / `sourceUrl` / `attribution` 은 입력 시점에 채운다.
나중에 "이거 어디서 가져왔더라"가 되면 복구가 안 된다.

## 의도적으로 뺀 것과 그 이유

### 타임스탬프 주석 (Annotation)

이 제품의 **차별점이 될 기능**이다. 곡의 특정 순간에 해설을 못 박고,
재생 중 자동으로 따라 흐르며, 주석을 누르면 그 지점으로 점프한다.
클래식판 Genius.

**1단계에서는 뺀다.** 이유는 둘이다.

1. Annotation 은 `recording_id` FK 하나만 무는 **리프 테이블**이라, 나중에 추가해도
   기존 테이블이 안 바뀐다. 마이그레이션 비용이 사실상 0이다.
2. 주석 기능은 주석 다는 스튜디오 화면까지 만들어야 의미가 있는데,
   그 전에 확인할 게 있다 — **곡 3개를 스토리까지 직접 채워봤을 때 그 작업이 재밌는가.**
   재미없으면 주석 기능은 영영 안 쓰는 화면이 된다.

나중에 싸게 붙이기 위해 1단계에서 두 가지를 지켜 두었다:
- `Recording.durationSeconds` 를 처음부터 채운다 (소급 입력은 고통스럽다)
- **플레이어를 어댑터로 감쌌다** (`static/js/player.js`) — `getCurrentTime()` / `seek()` 가
  처음부터 노출돼 있어, 주석을 붙일 때 플레이어 코드를 다시 쓰지 않아도 된다

**설계 결정: 주석은 Work 가 아니라 Recording 에 붙는다.**
"0:42에 첼로가 주제를 뒤집는다"의 0:42는 *그 연주에서의* 0:42다.
연주자가 바뀌면 템포가 달라 전부 어긋난다.
반대로 작곡 배경 스토리는 연주와 무관하므로 Work 에 붙는다.

### 악장 (Movement)

Recording 여러 개로 악장을 표현하지 **않는다.**

- **Recording** = "같은 것의 다른 버전" → 교체 가능, 하나만 고르면 됨
- **Movement** = "전체의 부분" → 순서대로 이어짐, 다 있어야 함

축이 다르다. 섞으면 `is_default` 규칙과 충돌하고
(교향곡 페이지에 1악장만 뜬다), 연주를 추가하는 순간 `[악장 × 연주]` 로 뒤섞인다.

**1단계 방침: 악장 자체를 Work 로 등록한다.** "월광 소나타 1악장"이 하나의 Work.
실제로 스토리가 있는 클래식은 대부분 단일 소품이거나 특정 한 악장이다.

전곡 묶음이 필요해지면 Movement 테이블이 아니라
**`Work.parentWork` self FK 두 컬럼**을 추가한다. 단일 소품에는 영향이 없다.

### 연주 선택 UI

모델은 이미 여러 Recording 을 허용하지만, 화면에는 `is_default` 하나만 보여준다.
나머지는 백업이다.

### 그 외

배치 스케줄러(`@Scheduled`), 회원가입, 댓글, 검색.

**영상 생존 확인은 배치 대신 클라이언트에서 한다.** YouTube IFrame API 의
`onError` 가 코드 100(삭제/비공개), 101·150(퍼가기 금지)을 준다.
아무도 안 보는 곡을 매일 확인하는 것보다, 실제로 방문된 곡에서 즉시 감지하는 쪽이 낫다.
`Recording.available` 은 수동 토글로 둔다.

## 스키마 관리 방침

**`ddl-auto: update` 를 쓰지 않는다.** update 는 컬럼을 **추가만** 하고
rename / 삭제 / 타입 변경을 반영하지 않는다. 필드명을 바꾸면 새 컬럼이 생기고
기존 데이터는 옛 컬럼에 남아 화면에서 사라진 것처럼 보인다.
무엇을 했는지 기록도 남지 않고 롤백도 안 된다.

이 프로젝트에서 특히 위험한 이유: **스토리 원고는 오직 DB에만 존재한다.**
코드는 git 에 있지만 원고는 날아가면 손으로 다시 써야 한다.

| 단계 | 설정 |
|---|---|
| 스키마가 흔들리는 동안 | `create-drop` — 매번 새로 만들어 드리프트를 쌓지 않는다 |
| 진짜 콘텐츠를 넣는 날부터 | Flyway `V1__init.sql` + `ddl-auto: validate` |

`validate` 는 엔티티와 실제 스키마가 어긋나면 **부팅을 막는다.**
조용히 망가지는 것보다 시끄럽게 실패하는 쪽이 낫다.

V1 스크립트는 손으로 쓰지 않는다:

```yaml
spring.jpa.properties.jakarta.persistence.schema-generation.scripts.action: create
spring.jpa.properties.jakarta.persistence.schema-generation.scripts.create-target: schema.sql
```

## 기술 스택

| | 선택 | 이유 |
|---|---|---|
| 뷰 | Thymeleaf (SPA 아님) | React 를 붙이면 "만들고 바로 확인" 루프가 2배 느려진다 |
| DB | H2(개발) → PostgreSQL(운영) | |
| 본문 | Markdown + commonmark-java | 혼자 쓰면 위지윅보다 빠르다 |
| 인증 | Spring Security 폼 로그인, 단일 계정 | 1인 운영이라 회원가입이 없다 |
| 외부 연동 | RestClient → YouTube oEmbed | API 키 불필요. 제목·채널·썸네일 자동 채움 |

### Spring 전환의 실제 비용

**Django admin 같은 게 없다.** 모델만 등록하면 공짜로 나오던 CRUD 화면을 직접 만들어야 한다.
그런데 이 제품은 혼자 콘텐츠를 채우는 게 핵심이라 **입력 화면이 제품의 절반**이다.
그래서 `admin/` 패키지를 1단계 스코프에 처음부터 포함시켰다.

### 등록 화면의 필수 장치

**oEmbed 가 200 을 줘도 내 사이트에서 재생된다는 보장이 없다.**
퍼가기 금지(101/150) 영상도 oEmbed 는 정상 응답한다.

그래서 음원 등록 화면에 **미리보기 플레이어**를 넣었다.
URL 을 붙여넣고 저장하기 전에 사람이 직접 한 번 재생해 본다.
이게 나중에 붙이는 어떤 배치보다 중요하다.

## 1단계 스코프

### 만드는 것
- 작곡가 / 곡 / 음원 CRUD (관리자용)
- 곡 목록, 곡 상세, 작곡가 목록·상세
- 유튜브 임베드 재생 + 어댑터로 감싼 플레이어
- 유튜브 URL 붙여넣기 → 제목·채널 자동 채움 + 미리보기

### 안 만드는 것
주석, 악장, 연주 선택 UI, 회원가입, 댓글, 검색, 배치

### 성공 기준

기능 개수가 아니다.

> **곡 3개를 스토리까지 직접 채워 넣고, 브라우저에서 읽으며 들었을 때
> "이거 계속 하고 싶다"는 느낌이 드는가.**

이 질문에 yes 가 나오면 2단계는 타임스탬프 주석이다.
no 가 나오면 만들 게 아니라 컨셉을 다시 봐야 한다.
